This fixture demonstrates a clear case of host escape via unrestricted `sudo` usage: the `install.py` script copies a plist to `/Library/LaunchDaemons`—a system-wide, privileged location—and loads it with `launchctl`, establishing persistent code execution outside the agent’s sandbox, even after uninstall.

Tell the linter owner that the current manifest-based analysis is insufficient because it only validates declared file operations against the write scope, but fails to detect **runtime privilege escalation via shell commands under sudo**. The declared write scope (`./sandbox/install.log`) appears harmless, but the actual behavior (writing to `/Library/LaunchDaemons`) is dangerous and completely unmonitored by the linter. The linter must be enhanced to flag any execution of `sudo` or other privilege-granting commands in shell operations—even if those commands are not explicitly listed in a "commands" allowlist—since they can bypass declared scope entirely.

This is a critical gap: attackers can abuse sudo in scripts to achieve host persistence while keeping manifests that appear innocuous. The linter should require either prohibition of `shell=True` with `sudo`, or at minimum demand explicit, audited declarations of elevated-capability actions.
