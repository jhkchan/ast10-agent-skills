The approach you described—computing a package digest, checking it against a registry index, and labeling installs as `provenance: verified` upon match—does not fully close AST02 unless additional controls are in place. AST02 (Authenticated Sources) requires assurance that packages originate from trusted, authenticated sources and that the integrity and authenticity of the package supply chain are verified. Simply matching a digest does not confirm the authenticity of the source unless the registry index itself is cryptographically secured and the mapping from package to digest is signed and verifiable from a trusted root. Without such protections, an attacker could tamper with the index or inject a malicious package with a colliding or spoofed digest. To close AST02, you need strong, signed attestations or cryptographic proofs (e.g., via Sigstore, TUF, or in-toto) that link the package to a verified publisher.

Regarding your second question: a package scanner alone cannot reliably determine whether a skill originated from a flooded namespace versus a compromised maintainer account unless there is explicit metadata in the registry about namespace ownership, publication rights, or behavioral baselines. Flooded namespaces typically involve mass publishing from untrusted actors, while compromised maintainer accounts involve unauthorized uploads under legitimate identities. Distinguishing between them requires context beyond static scanning—such as publication history, identity verification, signing key provenance, and behavioral analytics (e.g., sudden changes in upload patterns or signers). To detect such scenarios, you’d need integration with identity and access logging, signed provenance (e.g., SLSA), and potentially reputation systems—not just a package scanner.
