# Run 5 — the ten refused judgments, and what is left of them

**Ten of run 5's 198 attempted judgments never reached the pool, and the harness that
discarded them wrote nothing down.** `eval/scorecards/*.json` publishes 188 binding
judgments; three documents said the other ten "left an audit-trail entry naming the provider
and the round"; `config/audit.yml` said `runtime_entries: []` and had not been touched since
the commit that predates the first judged run. This file is the record that was supposed to
exist. It is written after the fact, from the only bytes that survived, and it is explicit
about the difference.

Nothing here is imputed into any published figure. No scorecard in `eval/scorecards*/` is
modified by this document, and no verdict is re-issued. This is a record of a gap.

## What survived, and what did not

| | Recoverable? | From what |
| --- | --- | --- |
| How many were refused, per skill | **Yes, exactly** | `rounds x providers` minus the judgments in the file |
| Which judge was refused, per skill | **Yes, exactly** | the providers absent from each round |
| Which round it happened in | **Yes, exactly** | the order judgments are appended in (see below) |
| Why it was refused | **No** | the `parse_judgment` message existed only in memory |
| Whether it was a refusal or a crash | **No** | same: `status` was never written |
| What the judge actually said | **No** | `raw_response` is stored only for judgments that pooled |

The last three are gone. Not "hard to find" — gone. `run_judge` built its `audit_trail` as a
local list, `eval/run_judge_matrix.py` kept only `res["judgments"]` from each round and then
deleted the per-round `.<skill>.round<n>.json` file that held the rest. No log of the run
survives either; the harness prints its per-round counts to stdout and that stdout was not
captured. **We cannot reconstruct the reasons or the responses, and no amount of care with
the remaining bytes will change that.**

One consequence deserves saying out loud, because the repository has been saying the
opposite: the claim that all ten were "refused as malformed for want of a justification" is
**not supported by anything on disk.** `status` was never recorded, so a Bedrock throttling
error and a judge that would not justify itself are indistinguishable in what remains. The
justification contract is the most likely explanation — it is the only refusal path this
prompt exercises often, and runs 3 and 4 lost 21 and 18 the same way — but "likely" is the
honest word, and prose that asserted the mechanism has been corrected to say so.

## How the round attribution is derived

`run_judge` calls the adapters in roster order and `run_judge_matrix` concatenates the rounds
in order, so a judgment's position in `card["judgments"]` carries its round. Within a round
the provider's index in `card["providers"]` strictly increases; a non-increase can only be
the start of the next round. Segmenting on that recovers each round's roster exactly, and
each round's absentees are its refusals.

This is checked rather than assumed. The segmentation is only accepted when it yields exactly
`card["rounds"]` segments, which it does for all eleven skills of run 5 (and for all eleven of
runs 3 and 4). An entirely empty round would leave no boundary to see and would show up as too
few segments; `scripts/refusal_ledger.py::rounds_from_order` returns `None` in that case and
the round is reported as unknown rather than guessed. The one assumption that cannot be
checked from inside the file is that the roster order did not change mid-run, which the
harness has no code path to do.

Every table below is generated by `python3 scripts/refusal_ledger.py --report`, and
`python3 scripts/refusal_ledger.py` fails if this file and the scorecards disagree.

## What the gap can and cannot do to the published numbers

The gap is not uniform noise: **AST01 lost the two judges that scored AST01 lowest.**
`bedrock/deepseek-v3.2` averages 100.5 on AST01 over its two surviving rounds and
`bedrock/nova-pro` averages 104.5, against a pooled mean of 110.1 — and both of their round-3
judgments are among the ten.

The table below asks one what-if and one only: if each refused attempt had scored that judge's
own observed mean on that skill, what would the gate have said? It is a sensitivity check, not
a correction. The imputed values are **not** written into any scorecard, dashboard, or README
figure, and the published verdicts stand as issued.

It is also not hand-arithmetic any more. `eval/robustness.py` runs exactly this computation
through the live gate, `python3 eval/calibration.py` prints it and writes it to
`eval/robustness.json`, `docs/skill-judge-dashboard.md` publishes it beside the ship count, and
`tests/test_robustness.py` fails if any row here, there, or in the JSON disagrees with the
corpus.

| Skill | Published n | Published mean | Published `ci_lower` | Verdict | What-if n | What-if mean | What-if `ci_lower` | What-if verdict |
| --- | ---: | ---: | ---: | --- | ---: | ---: | ---: | --- |
| AST01 | 16 | 110.1 | 108.4 | SHIP | 18 | 109.2 | 107.6 | **BLOCKED** |
| AST03 | 16 | 112.2 | 111.0 | SHIP | 18 | 112.3 | 111.3 | SHIP |
| AST05 | 16 | 110.6 | 109.4 | SHIP | 18 | 110.9 | 109.8 | SHIP |
| AST06 | 16 | 112.1 | 111.1 | SHIP | 18 | 112.0 | 111.0 | SHIP |
| AST07 | 17 | 110.2 | 109.0 | SHIP | 18 | 110.2 | 109.1 | SHIP |
| advisory | 17 | 112.2 | 111.1 | SHIP | 18 | 112.4 | 111.4 | SHIP |

Five of the six affected skills are insensitive to the gap; their what-if verdict is the
verdict they were issued. **AST01 is not.** Its published `ci_lower` of 108.4 clears the bar by
0.4, and the single most natural assumption about its two missing judgments puts it at 107.6,
which is `BLOCKED`. That is the honest status of the eleventh ship: it depends on two
judgments nobody can produce.

The direction is an artefact of the assumption, and the assumption is load-bearing. Imputing
at the pooled mean instead would leave every mean untouched and shrink every `sem`, turning
the gap into free confidence. Neither assumption is knowable from what survived. That is the
argument for recording refusals rather than reasoning about them.

## What stops this happening again

1. **`scripts/judge_harness.py::run_judge` persists every refusal** through
   `adapters.base.record_failure`, the append-only path in `config/audit.yml` that a crashed
   adapter already used. Each entry carries the skill, the 1-based round, the status
   (`malformed` or `failed`), the parse error verbatim, and a redacted, truncated excerpt of
   the offending response with its original length. The dict returned in `audit_trail` is the
   dict written to disk, so the two cannot disagree, and there is no argument value that means
   "do not record".
2. **`eval/run_judge_matrix.py` copies those entries into the scorecard** as `attempted`,
   `pooled`, `refusals` and `refusals_by_provider`, so a reader holding one scorecard can see
   that file's own gaps without leaving it.
3. **`scripts/refusal_ledger.py` fails the build** if any scorecard's pooled `n` is below its
   attempted `n` without a matching record — in the scorecard for anything the fixed harness
   wrote, or in this file for the frozen corpora that predate it. The exemption is keyed on the
   absence of the `attempted` field, not on a directory name, so the next run cannot inherit it.
4. **`tests/scripts/test_refusal_recording.py`** runs a judgement against a deliberately
   malformed adapter and asserts the refusal reaches the persisted file, and
   **`tests/test_refusal_ledger.py`** runs the guard over this repository's real scorecards.
